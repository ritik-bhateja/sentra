# Migration Guide: Chat Messages V2 (Better Sequencing)

## What's Improved

### ✅ Better Message Sequencing
- **Auto-incrementing sequence_number** per session
- **Guaranteed ordering** even with identical timestamps
- **No race conditions** when messages sent rapidly

### ✅ Better Primary Key
- **BIGSERIAL id** as primary key (auto-incrementing)
- **message_id** kept as unique index for compatibility
- **Faster queries** with integer primary key

### ✅ Flexible Content Storage
- **JSONB column** can store both strings and objects
- **No type mismatch** between frontend and backend
- **Future-proof** for rich content (images, charts, etc.)

## Schema Changes

| Column | Old | New | Change |
|--------|-----|-----|--------|
| `id` | ❌ None | ✅ BIGSERIAL PK | Added auto-incrementing primary key |
| `message_id` | PK | UNIQUE | Changed to unique index |
| `sequence_number` | ❌ None | ✅ INTEGER | Added auto-incrementing per session |
| `content` | JSONB | JSONB | Same (but now handles strings too) |

## Migration Steps

### Option 1: Fresh Start (Recommended for Development)

```bash
# 1. Backup existing data (if needed)
pg_dump -h <host> -U postgres -d company_db -t chat_messages > backup_messages.sql
pg_dump -h <host> -U postgres -d company_db -t chat_sessions > backup_sessions.sql

# 2. Drop old tables
psql -h <host> -U postgres -d company_db -c "DROP TABLE IF EXISTS chat_messages CASCADE;"
psql -h <host> -U postgres -d company_db -c "DROP TABLE IF EXISTS chat_sessions CASCADE;"

# 3. Create new schema
psql -h <host> -U postgres -d company_db -f database_schema_v2.sql

# 4. Update models in code
# Rename models_v2.py to models.py
mv models.py models_old.py
mv models_v2.py models.py

# 5. Restart application
python3 Agent_Trigger.py
```

### Option 2: In-Place Migration (For Production)

```sql
-- 1. Add new columns to existing table
ALTER TABLE chat_messages ADD COLUMN id BIGSERIAL;
ALTER TABLE chat_messages ADD COLUMN sequence_number INTEGER;

-- 2. Populate sequence_number for existing messages
WITH numbered_messages AS (
    SELECT 
        message_id,
        ROW_NUMBER() OVER (PARTITION BY session_id ORDER BY timestamp) as seq
    FROM chat_messages
)
UPDATE chat_messages m
SET sequence_number = nm.seq
FROM numbered_messages nm
WHERE m.message_id = nm.message_id;

-- 3. Make sequence_number NOT NULL
ALTER TABLE chat_messages ALTER COLUMN sequence_number SET NOT NULL;

-- 4. Add unique constraint
ALTER TABLE chat_messages ADD CONSTRAINT unique_session_sequence 
    UNIQUE (session_id, sequence_number);

-- 5. Change primary key
ALTER TABLE chat_messages DROP CONSTRAINT chat_messages_pkey;
ALTER TABLE chat_messages ADD PRIMARY KEY (id);
ALTER TABLE chat_messages ADD CONSTRAINT unique_message_id UNIQUE (message_id);

-- 6. Add trigger for auto-incrementing sequence_number
CREATE OR REPLACE FUNCTION set_message_sequence_number()
RETURNS TRIGGER AS $$
BEGIN
    SELECT COALESCE(MAX(sequence_number), 0) + 1
    INTO NEW.sequence_number
    FROM chat_messages
    WHERE session_id = NEW.session_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trigger_set_message_sequence
    BEFORE INSERT ON chat_messages
    FOR EACH ROW
    WHEN (NEW.sequence_number IS NULL)
    EXECUTE FUNCTION set_message_sequence_number();

-- 7. Update indexes
DROP INDEX IF EXISTS idx_session_messages;
CREATE INDEX idx_session_messages ON chat_messages(session_id, sequence_number);
CREATE INDEX idx_session_timestamp ON chat_messages(session_id, timestamp);
```

## Benefits

### 1. **Guaranteed Message Order**
```sql
-- Old way (could have issues with identical timestamps)
SELECT * FROM chat_messages WHERE session_id = 'xxx' ORDER BY timestamp;

-- New way (guaranteed correct order)
SELECT * FROM chat_messages WHERE session_id = 'xxx' ORDER BY sequence_number;
```

### 2. **No Race Conditions**
```
User sends: "Hello" (timestamp: 1000)
Bot replies: "Hi!" (timestamp: 1000)  ← Same timestamp!

Old: Order undefined (could show bot message first)
New: sequence_number ensures correct order (1, 2, 3...)
```

### 3. **Better Performance**
```
Old PK: VARCHAR(50) - 50 bytes per index entry
New PK: BIGINT - 8 bytes per index entry
Result: 6x smaller indexes, faster queries
```

### 4. **Easier Debugging**
```json
{
  "id": "1780317569105",
  "type": "user",
  "content": "Show policies",
  "timestamp": 1780317569105,
  "sequence": 1  ← Easy to see message order
}
```

## Monitoring

After migration, monitor:

1. **Message order correctness**
   ```sql
   SELECT session_id, COUNT(*) as msg_count, 
          MAX(sequence_number) as max_seq
   FROM chat_messages 
   GROUP BY session_id 
   HAVING COUNT(*) != MAX(sequence_number);
   ```
   Should return 0 rows (count should equal max sequence)

2. **Sequence gaps** (shouldn't exist)
   ```sql
   SELECT m1.session_id, m1.sequence_number + 1 as missing_seq
   FROM chat_messages m1
   LEFT JOIN chat_messages m2 
     ON m1.session_id = m2.session_id 
     AND m1.sequence_number + 1 = m2.sequence_number
   WHERE m2.sequence_number IS NULL
     AND m1.sequence_number < (
       SELECT MAX(sequence_number) 
       FROM chat_messages 
       WHERE session_id = m1.session_id
     );
   ```
   Should return 0 rows

3. **Performance**
   ```sql
   EXPLAIN ANALYZE 
   SELECT * FROM chat_messages 
   WHERE session_id = 'xxx' 
   ORDER BY sequence_number;
   ```
   Should use index scan, not sequential scan

## FAQ

**Q: Do I need to update the frontend?**
A: No, the frontend doesn't need any changes. The `sequence_number` is transparent.

**Q: What if two messages have the same timestamp?**
A: The `sequence_number` ensures correct ordering regardless of timestamp collisions.

**Q: Can I still query by timestamp?**
A: Yes! The `timestamp` column is preserved and indexed for time-based queries.

**Q: What happens to existing messages?**
A: In-place migration assigns sequence numbers based on timestamp order. Fresh start loses old messages (backup first!).

**Q: Is this backward compatible?**
A: Yes! The API endpoints and response format remain unchanged.

## Recommendation

For **development/testing**: Use **Option 1 (Fresh Start)**
For **production**: Use **Option 2 (In-Place Migration)** with proper backups

The improved schema provides better reliability, performance, and debugging capabilities with minimal code changes! 🎉
